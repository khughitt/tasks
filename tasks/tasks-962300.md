relay records a process handle only for a harness attached to a terminal: every adapter's resolveAgentPid filters on p.tty !== null (relay src/adapters/{claude-code,codex,opencode}.js). A headless harness session — a detached, CI, or cloud agent — is therefore published with process: null.

src/relay/resolve.rs builds same_process by filtering on agent.process.is_some(), so a handle-less row is dropped before no_match() ever sees it, and the caller gets the generic 'no relay agent matches the nearest <comm> ancestor, pid N'. The agent is in fact present and correctly identified; only its handle is absent, and the operator has no way to tell those two situations apart.

Refusing is right — falling back to terminal identity in scope is exactly what the design forbids. Only the diagnostic is wrong. Name the case: an agent whose harness and session match this ancestor but carries no process handle should say so, and say that relay records one only for a harness with a controlling terminal, alongside the existing TASKS_SESSION recovery.

Scope: the no_match() diagnosis in src/relay/resolve.rs plus a refusal case in its test module. The matching rules do not change.
