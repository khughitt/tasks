Why: the report asked for `--body-file` or `--body -` on `tasks edit`, so agents can pass long multi-line bodies without shell substitution. `edit --body -` has read the body from stdin since 4a72b50 (2026-08-29; src/commands/edit.rs, the `Some("-")` branch), but nothing says so: `--body` has no help text on `add` or `edit`, and skills/tasks/SKILL.md never mentions it. `add` shares the same `--body` field (`FieldArgs` in src/cli.rs) but has no stdin branch, so `printf 'a\nb\n' | tasks add y --body -` stores the literal body `-`, a silent wrong write (scratch project, 2026-10-18). Priority 3: `edit --body -` works today.

Reported as: "tasks edit takes a body only inline (--body); a --body-file (or --body -) would let agents pass long multi-line bodies without shell substitution" (from nodes).

Decided at scoping: no `--body-file`. `--body -` with redirection (`--body - < body.md`) already covers a file, matches `attach -`, and needs no new option row in ops's cli.toml.

Done:
- `add --body -` reads the body from stdin as `edit` does, with the read shared in one place.
- `--body` gets help text on `add` and `edit`: the body text, or `-` to read it from stdin.
- skills/tasks/SKILL.md names `--body -` for multi-line bodies (e.g. `tasks edit <id> --body - < body.md`) where it lists the add and edit options.
- Tests in tests/cli.rs: a multi-line body piped to `add` and to `edit` round-trips through `show`.
- tools/cli.toml is unchanged, because the rows keep `value = "string"`, and `parser_surface_equals_table` still passes.

Where to look: src/cli.rs (`FieldArgs.body`), src/commands/edit.rs (stdin branch), src/commands/add.rs, skills/tasks/SKILL.md (the edit option list and the scoped-task `add` line).
