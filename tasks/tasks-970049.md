Why: Codex task stamps (agent, model) carry only 'codex', so model attribution in obs covers Claude Code only (goal hq-fce47e, which depends on this task beside relay-2cd4b1 and lore-f71994).

The consumer half of the lore brief's alternative 1 (§5, from hq-1bd166): when TASKS_AGENT is exactly 'codex', call relay's resolver and stamp agent codex/<model> and the completion model from its output; when it answers bare 'codex', stamp the harness alone, never a config default (instruction-provenance T13). The resolver is valid only inside a tool call, which is where tasks runs.

Established (checked 2026-10-17 at 8e1ff08 and relay docs/api.md):
- relay-2cd4b1 is done. Contract: relay `docs/api.md` "Codex model resolution". `relay model --harness codex --json` prints one object `{verified, agent, harness, model, effort, thread, rollout, reason}`; every answer exits 0, with `reason` one of no-thread, not-under-codex, no-rollout, ambiguous-rollout, no-turn-context, scan-limit, earlier-turn, turn-boundary. A failure exits 1 with kind `model_failed`. "A caller that needs a stamp treats a failure, or no answer within 2 s, like an unverified answer and reports it." `--pretty` prints the agent alone; `RELAY_FORMAT` changes the default mode, so the call names its mode.
- relay-96422d (todo) clarifies, without changing behaviour: model/effort are null on an unverified answer, effort may be null when verified, and the failure-code list is not exhaustive. Read `verified` and `model`, and treat any non-zero exit as a failure; no edge on it is needed.
- tasks reads the stamps in `src/commands/mod.rs`: `creation_agent` (TASKS_AGENT, or explicit `--agent`) for add (`src/commands/add.rs` ~108) and feedback (`src/commands/feedback.rs` ~249), and `completion_model` (TASKS_MODEL) for done (~1586), both through `provenance_var`. The only subprocess tasks spawns today is `wl-paste` (`src/clipboard.rs`); `src/relay/` reads relay's registry snapshot, never the relay CLI.
- Codex sets TASKS_AGENT = "codex" in hq `codex/config.toml` (~227 `shell_environment_policy`); no Codex variable carries the model (brief §5).
- **Deployment gap:** `relay` is not on PATH on titan (2026-10-17; relay ships `bin/relay.js` as its npm bin). lore-f71994's `$(relay model ...)` needs it too, so it is a shared prerequisite owned by relay/hq, not something tasks installs.

Decide in the spec (planned), with these leans:
- Lookup: `relay` on PATH. A missing binary is a failure: stamp bare `codex` and warn naming the cause. No configured fallback path.
- Precedence: explicit `--agent` and a set TASKS_MODEL win; the resolver runs only when TASKS_AGENT is exactly `codex`, at most once per command, with a 2 s budget (kill on expiry).
- Reporting: an unverified answer or failure adds a warning carrying relay's reason (or exit and stderr), and the stamp stays the harness alone. Decide whether `no-thread` (hooks) warns.
- Amend `docs/specs/2026-09-10-model-provenance-design.md` "Supply" for the Codex route; README (~189-192) and `skills/tasks/SKILL.md` follow.

Done: under TASKS_AGENT=codex, add/feedback stamp `codex/<model>` and done stamps `model` when relay verifies, and the harness alone plus a warning otherwise. Tests in `tests/cli.rs` use a fake `relay` script on PATH: verified, unverified with a reason, exit 1, timeout, and missing. One live run in a Codex session records a verified stamp once relay is on PATH there.
