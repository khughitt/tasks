Why: `tasks edit` has a `--no-*` clearing flag for every optional field except the doc links, so a stale `spec`, `plan`, or `step` can only be removed through the `$EDITOR` path, which an agent cannot drive. Three sessions hit this (this report, tasks-980a39, tasks-0f8043): a goal kept its `--step` after its plan was split into step children, and dropped step tasks kept links to merged headings.

Done when: `edit` accepts `--no-spec`, `--no-plan`, and `--no-step`, each `conflicts_with` its setter like the other `--no-*` flags in `src/cli.rs` (EditArgs). `--no-plan` while a step remains is refused by the existing "--step requires a plan" validation in `src/commands/mod.rs` (the field-apply path), so clearing a plan takes `--no-plan --no-step`; that is the fail-early choice over silently clearing the step too. Tests in `tests/cli.rs` cover each flag, the refusal, and the conflicts; `skills/tasks/SKILL.md` lists the new flags in its `tasks edit` line; completion picks them up from clap.

Where to look: `src/cli.rs` EditArgs, `src/commands/edit.rs` (the flag path near `args.no_source`), `src/commands/mod.rs` link validation.

Original report: tasks edit <id> --no-plan / --no-step / --no-spec do not exist. After a planned goal's single-task plan was split into step children, the goal kept its own --step link to the first heading; the only way to remove it is hand-editing the record, which the protocol forbids. Expected a clearing flag alongside the other --no-* flags.
